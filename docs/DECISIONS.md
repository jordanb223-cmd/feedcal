# Decisions

Each entry: date, decision, why, and what would change it.

## D1 — Supabase for data, auth, storage, jobs (2026-11-20)
Postgres with RLS lets the database itself enforce who can see a feed. Auth, Storage, Queues (pgmq), pg_cron and Edge Functions come in one platform. Would change if Edge Function time limits block core processing (see D6).

## D2 — Cloudflare for domain, web and inbound email (2026-11-20)
Supabase can't receive email; Cloudflare Email Routing can hand mail to a Worker. Pages serves calendar files with custom headers and caching. GitHub Pages isn't used: Pages sites are public and GitHub limits commercial use (`UNVERIFIED` — check current GitHub Pages docs).

## D3 — GitHub for code, CI and deploys (2026-11-20)
Repo on GitHub (public since D19), Actions for checks and deploys, Dependabot, gitleaks (D20).

## D4 — Forwarding before the Gmail API (2026-11-20)
A forwarding address per feed needs no access to anyone's mailbox, so no Google restricted-scope review. The Gmail connection (Phase 17) needs `gmail.readonly`, a restricted scope (`UNVERIFIED` — confirm review steps and timing in Google's current docs before Phase 17).

## D5 — Buy Me a Coffee for donations (2026-11-20)
No card data on our servers. Webhooks are signature-checked (header and algorithm `UNVERIFIED` until Phase 15).

## D6 — Cloudflare Worker fallback for oversized PDFs (2026-11-20)
Large PDFs may exceed Edge Function time or memory limits. A Worker processor takes over only for those files.

## D7 — Hono on Cloudflare Pages advanced mode (2026-11-20)
The plan allowed Hono or SvelteKit. Hono is chosen: small, server-rendered HTML fits "no heavy SPA," and it runs unchanged in Pages, Workers and Vitest. The app is bundled by esbuild into `dist/_worker.js`; version and commit are injected at build time.

## D8 — npm workspaces (2026-11-20)
No extra tool to install. Packages export TypeScript source directly (`exports: ./src/index.ts`); the web build bundles them.

## D9 — Feed tokens stored as hash + Vault-encrypted copy (2026-11-20)
From BUILD-PLAN revision 1. Lookup uses SHA-256 of the token; the owner can view the link again from a Vault-encrypted copy. Implemented in Phase 2.

## D10 — Health probe via an anon-callable RPC (2026-11-20)
`public.health_check()` returns `true` and reads no tables, so exposing it to `anon` reveals nothing. The web app never holds the service-role key.

## D11 — Column-level grants on top of RLS (2026-11-20)
RLS decides which rows a role can see; it can't hide columns. Supabase's default table grants are revoked, and each role is granted only the columns it needs. Token columns are granted to nobody but the service role; the SECURITY DEFINER token functions read them. Anon reads public-safe columns of public feeds and their published events. Signed-in non-members read public pages through `public_feed_page()`, not the tables, so evidence quotes stay with the feed's members. Cost: app code must list columns instead of using `select *`.

## D12 — Policy helpers in a `private` schema (2026-11-20)
`private.is_feed_member()`, `private.feed_role()` and similar are SECURITY DEFINER with `search_path = ''`. They let policies on `feeds` and `feed_editors` check membership without recursing through each other's RLS. The schema isn't exposed by the API.

## D13 — Feed token minted by a trigger (2026-11-20)
Every feed gets a token on insert, in the same transaction as its Vault secret, so a failed insert leaves no orphan secret. Deleting a feed deletes its secret. Vault functions used: `vault.create_secret(new_secret, new_name, new_description, new_key_id)` and `vault.update_secret(secret_id, new_secret, ...)`, reading through `vault.decrypted_secrets`. These signatures were read from the local stack (`supabase_vault` 0.3.2). Hosted behaviour is `UNVERIFIED`; check it on the first staging deploy. Docs: https://supabase.com/docs/guides/database/vault

## D14 — public_feed_page returns upcoming events only (2026-11-20)
A subscribe page shows the next few events; returning a feed's whole history to anon is unnecessary exposure. It returns at most 200 events, with a default of 50. See the recurring-event gap in DATA-MODEL.md.

## D15 — Session checks ask the Auth server (`getUser`), not `getClaims` (2026-11-20)
Found while testing Phase 3. The local stack signs access tokens with ES256 (`kid` present). For those, `@supabase/supabase-js` 2.119.2 `getClaims()` checks only the signature against the public key and never asks the server. After "sign out everywhere", the old cookies still opened `/account`. The Auth server itself answered `403 session_not_found` for the same token. `currentUser()` now calls `getUser()`. That's one extra request per signed-in page, and revoked sessions stop working at once. Public pages and feed URLs don't check sessions, so they don't pay this cost.

## D16 — Magic links verified by our server, behind a button (2026-11-20)
The email template links to `/auth/confirm?token_hash=…&type=email`, which is Supabase's server-side "token hash" pattern. The GET only shows a "Sign in" button; the POST calls `verifyOtp`. Email security scanners that open links automatically therefore can't use up the one-time link. Because the error comes back to our server, it can say "expired or already used" in plain English. Docs: https://supabase.com/docs/guides/auth/server-side/email-based-auth-with-pkce-flow-for-ssr

## D17 — CSRF: double-submit cookie plus an origin check (2026-11-20)
Every POST must carry an `Origin` (or, failing that, `Referer`) equal to the site's own origin, and a form token equal to an HttpOnly cookie (`__Host-feedcal_csrf` over HTTPS). Either check failing returns 403 before any handler runs. The app has no JSON API yet; origin checks cover future API routes.

## D18 — Account deletion: SQL purge plus an Edge Function (2026-11-20)
`request_account_deletion()` stamps `profiles.deleted_at`. After 14 days, `due_account_deletions()` lists the account. `purge_account_data()` hands each owned feed to its longest-standing editor, deletes feeds with no editor (their Vault secrets go too), and wipes the name and revision actor. The `delete-accounts` Edge Function then deletes the auth user. The function only accepts the service-role key. **Scheduling it is not set up yet** (see SETUP.md).

## D19 — Public repository (2026-11-20)
GitHub's docs say that on GitHub Free, private repositories get no environments, no environment secrets, no branch protection and no rulesets. All of these work for public repositories. The deploy design (D3, CONTRIBUTING.md) needs them. The owner chose public over paying for GitHub Pro. Secrets stay in GitHub encrypted secrets, which aren't visible to the public. Before publishing, the commit history was rewritten so that commits carry GitHub's no-reply address and the plan carries no full name. The clean history went to a new repo, so the old commits aren't reachable by hash on a public repo. Docs: https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments and https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches

## D20 — Secret scan runs the gitleaks CLI over full history (2026-11-20)
`gitleaks-action@v2` scans only the pushed range (`<first>^..<last>`). That failed on the repo's first push, because the root commit has no parent. CI now downloads gitleaks 8.30.1, checks its SHA-256 against the release's checksums file, and scans the whole history on every run. That also covers rewritten or force-pushed history.

## D21 — Deploys need no database password; Pages settings come from the deploy script (2026-11-20)
- **No database password.** Supabase CLI 3.2.0 connects with the access token alone when `--remote` is used without `--password`. Its `db push --help` lists "Scoped access token … database_write" for that case. The CI secrets are therefore only `SUPABASE_ACCESS_TOKEN` and `CLOUDFLARE_API_TOKEN`. The old workflow also had two bugs this fixes: `db push` without `--remote` targets the *local* database in CLI 3.x, and `functions deploy` no longer takes `--project-ref`.
- **Pages settings per project.** Each Pages project deploys `main` as its production environment, so `wrangler.toml` `[env.production.vars]` would have labelled staging "production". `wrangler.toml` now has no vars. `.github/scripts/deploy.sh` sets `ENVIRONMENT`, `SUPABASE_URL` and `SUPABASE_ANON_KEY` on each Pages project, reading the public key with `supabase projects api-keys`. It also creates the Pages project if it's missing. Local values live in `apps/web/.dev.vars`.
- **Not yet checked:** the JSON field names from `supabase projects api-keys` (the script accepts both known shapes), and that `pages.dev` gives the projects their exact names. Both are confirmed by the first deploy.

## D22 — Calendar output: local times with generated VTIMEZONEs (2026-11-20)
- **Local times.** Timed events are written in their own zone (`DTSTART;TZID=America/Los_Angeles:…`) with a VTIMEZONE built from the runtime's IANA data (`Intl`). So a weekly 5:30pm practice stays at 5:30pm across daylight saving, which a UTC-only feed gets wrong.
- **How the VTIMEZONE is built.** Each offset change in the years the events touch is its own observance, with no RRULE. That is valid RFC 5545 and doesn't guess future rules. Recurring events get 5 years of coverage. Past that, calendar apps fall back to their own data for the IANA name.
- **Found in review:** the first version put the spring-forward change at 01:00 instead of 02:00. The tests missed it; reading the golden file caught it. Tests now pin exact change times for Los Angeles, Sydney and Adelaide, plus an event in the hour after a change.
- **Stable output.** `DTSTAMP` is the event's last change, not the request time. Identical data gives a byte-identical file and the same ETag, so `If-None-Match` gets a 304.
- **All-day events.** `starts_at` is any instant on the first day and `ends_at` any instant on the last day, both read in the event's zone. `DTEND` is the day after the last day (exclusive).
- **Validation.** Golden-file tests, plus ical.js (Mozilla's parser, MPL-2.0, test-only) parsing every file. Each timed event's start must read back as the original instant.
- **Gaps.**
  - (Closed in Phase 10, D31: `events.exdates`.) The schema has no EXDATE column, so a single occurrence of a recurring event can't be skipped yet. Phase 10 needs this for updates.
  - Apple, Google and Outlook subscriptions are untested, because they need a hosted deploy.

## D23 — Subscribe page and links (2026-11-20)
- **The page carries the link.** `public_feed_page` returns the subscription token for public and unlisted feeds. A public feed's link is public by design (Rev 1); an unlisted page is reached only through its unguessable slug, so its link is exactly as secret as the page. Private feeds have no page.
- **Link formats are community-sourced; neither vendor documents them officially.**
  - Google: `https://calendar.google.com/calendar/r?cid=<url-encoded webcal URL>`. Seen in a Google Calendar Help Community thread and several developer write-ups.
  - Outlook: `https://outlook.live.com/calendar/0/addfromweb?url=…&name=…` (and `outlook.office.com` for Microsoft 365). Described as "never documented" by Microsoft (dev.to write-up).
  - The page always shows the plain link with a copy button, plus Android fallback steps.
  - Recheck all of these in the Phase 5 phone test (docs/TESTING.md).
- **Tap counting without JavaScript.** Buttons go through `/c/<slug>/go/<app>`, which counts the tap and then redirects. "Copy link" reports with a same-origin POST. The counts hold no personal data. Anyone can inflate them: that's accepted, and they're shown only as "taps", never as subscribers.
- **Count wording (Rev 4).** "At least N calendars follow this", with a line saying how it's counted (distinct calendar clients over 7 days; Google counts once for all its users).
- **Share kit.** `/feeds/<id>/share` replaces `/feeds/<id>/link` (which now gets a 301). Rotation redirects back to it after the POST, so refreshing can't rotate twice. QR codes are server-side SVG from `uqr` (MIT, no dependencies, works in Workers).
- **Found while testing:** the Phase 2 seed left `auth.users` token columns NULL, so seeded people couldn't sign in. Fixed; `005_seed_users_can_sign_in.test.sql` guards it.

## D24 — State machines live in the database; code and docs are generated from it (2026-11-20)
- **The survey** found eight implicit state machines (docs/STATE-MACHINES.md). Four were status columns that any value could jump to. Account deletion's "14 days" was written in five places.
- **Decision.** The database is the single source of truth.
  - `private.state_transitions` lists every legal move, and one trigger (`private.enforce_transition`) refuses any other move on UPDATE. Its error names the allowed moves.
  - `public.state_machines()` exposes the rules. `npm run db:states` generates `state-machines.generated.ts` and the diagrams, the same pattern as `db:types`, and CI fails if they're stale.
  - Hand-written labels are typed against the generated states, so a new state without a label won't compile.
- **Why the database, not TypeScript.** Phases 6–12 will change these columns from Edge Functions, SQL jobs and the web app. Only the database sees every writer.
- **Effect on users (UX):** clear status labels, and edits that actually reach subscribers' calendars (below). **On developers (DX):** one place to change a rule, generated types, errors that say what's allowed. **On AI agents (AX):** rules readable from one function and one doc; a wrong move fails loudly with the fix in the message, not silently.
- **Without breaking anything:** inserts aren't restricted, and every existing test passes unchanged (152 database tests).
- **Bug fixed along the way.** Nothing raised an event's `SEQUENCE` on edits, and calendar apps use it to decide whether an edit is newer. `private.events_bump_sequence` now raises it on any change a subscriber can see, unless the caller already raised it.
- **One grace period.** `private.deletion_grace()` defines it; `request_account_deletion`, `due_account_deletions` and the new `account_status()` read it; the account page shows what `account_status()` returns.

## D25 — Quick wins before Phase 6 (2026-11-21)
- **Error pages.** A request that accepts `text/html` gets an HTML 404/500 page: what happened, what to try, and the request id. `/health`, `/f/*` and `/.well-known/*` always answer as machines. Error details never reach the page; they're logged by name only.
- **The login form keeps the typed address** on every failure (escaped). The other forms have no typed fields (checkboxes and buttons only), so they had nothing to keep.
- **International addresses (RFC 6531) are refused, with a clear message.** Tested against the local Auth server (GoTrue v2.198.0) on 2026-11-21: `pelé@example.test` and `user@bücher.example` both return `validation_failed: invalid format`. Hosted Auth was not tested (UNVERIFIED that it matches; it runs the same open-source server). Revisit if GoTrue adds support.
- **Session timeouts are not available on the free plan.** supabase.com/pricing lists "Session timeouts: Not included in free" (checked 2026-11-21); docs: supabase.com/docs/guides/auth/sessions. No idle or absolute limit is set. Sessions end on sign-out, "sign out everywhere", or refresh-token expiry. Set 30 days absolute / 7 days idle if the projects move to Pro.
- **Our own sign-in email limit:** 5 per address and 20 per IP per rolling hour (`public.login_attempt_allowed`, limits in `private.login_limits()`). Stored as salted sha256 hashes, pruned every call. Refused attempts aren't counted. If the check fails, sign-in fails closed with a "try again in a minute" message. Known limit: anyone can use up an address's 5 attempts for an hour, by the form or by the RPC; that's the cost of any per-address limit.
- **Stranger test against the real stack.** `tests/integration/stranger.test.ts` signs Alice and Bob in with real sessions and proves Bob gets 404 on Alice's share kit and flyer and can't rotate her link, which keeps working. CI runs it in the database job.
- **Vulnerability reports** go through GitHub private vulnerability reporting (turned on 2026-11-21), so no email address is published. `/.well-known/security.txt` points at it; a test fails 30 days before its `Expires` date.
- **CHANGELOG.md** is written for organizers. The production deploy fails if the tag has no `## [X.Y.Z]` section.
- **Runbook:** docs/runbooks/stolen-laptop.md.

## D26 — Email intake by forwarding (2026-11-21)
- **Flow.** Cloudflare Email Routing (catch-all on `in.<domain>`) → Email Worker → `ingest-start` (HMAC) → one-time signed upload to the private `inbound-raw` bucket → `ingest-commit` (HMAC) → SQL `ingest_commit` → pgmq `process_message`. The Worker holds only `INGEST_HMAC_SECRET` and the public Supabase URL. It reads nothing but the size and the address.
- **Signing.** HMAC-SHA256 over `timestamp.body`, refused if more than 5 minutes off. One pinned test vector, checked with `openssl`, is asserted on both sides.
- **Addresses.** `feed-` + 20 base32 characters (100 random bits, no modulo bias since 256 = 8 × 32). Owners can rotate them. Members only can read them.
- **Headers are read in `ingest-commit`, never in the Worker.** Message-ID, From, Subject (RFC 2047 decoded), the first `Authentication-Results`, an approximate attachment count (`Content-Disposition: attachment` lines), and sha256 of the body below the headers. Full MIME parsing is Phase 7.
- **Authentication results.** Cloudflare's Workers docs say Email Routing checks DMARC and prepends one `Authentication-Results` header with authserv-id `mx.cloudflare.net`; only that first header is trusted (developers.cloudflare.com/email-service/api/route-emails/email-handler/, checked 2026-11-21). DMARC `fail` → quarantine even for a trusted sender. A missing header records nothing and doesn't quarantine on its own.
  - Risk: a Cloudflare community thread (Oct 2025) reports Email Routing dropping Gmail-forwarded mail on DMARC alignment. UNVERIFIED for our case; step 6 of the Phase 6 hand test checks it.
- **Allowlist.** The first mail from a sender creates an untrusted `sources` row and waits (`quarantine_reason = new_sender`). "Yes" trusts the sender and queues its waiting mail; "No" blocks it, ignores its waiting mail, and drops later mail quietly (no bounce).
- **Gmail confirmation.** Sender `forwarding-noreply@google.com` and subject `(#<digits>) Gmail Forwarding Confirmation - Receive Mail from <address>`. Both come from Gmail Help Community threads and forum posts; Google's own help pages don't spell them out (UNVERIFIED until the hand test). Captured only if DMARC passed, and the link is kept only if it's on `mail-settings.google.com` or `mail.google.com`. Shown on the page, never clicked by us.
- **Limits** (`private.intake_limits()`): 20 MB, 10 attachments, 50 accepted emails per feed per 24 hours. Over-limit mail is bounced with a plain reason. Duplicates and blocked senders are accepted silently.
- **Dedupe** on Message-ID or body sha256, per feed; idempotent commit (a ticket returns its first result).
- **Failures on our side throw instead of bouncing,** so the sending server can retry. That Cloudflare turns a thrown error into a temporary SMTP failure is UNVERIFIED; check it in the hand test.
- **Expiry.** Messages expire after 30 days. SQL can't delete stored files (`storage.protect_delete` refuses it), so deleting a message queues its file in `private.storage_trash`. pg_cron runs `private.expire_intake()` daily at 03:17 UTC, then calls the `storage-trash` Edge Function through pg_net, which deletes the files through the Storage API. The deploy script writes the function URL and the public anon key into `private.app_settings`, using the Management API's "Run sql query" endpoint (documented as experimental). `storage-trash` only deletes files already queued, so a stranger calling it changes nothing.
- **Owner screen** `/feeds/<id>/email`: the address, the Gmail confirmation, waiting senders, suspicious mail, setup guides, and a new-address button.
- **Not done here, by design:** nothing consumes `process_message` yet (Phase 7). The Worker isn't deployed and Email Routing isn't set up, because both need the domain (SETUP §7).

## D28 — Parsing forwarded email (Phase 7, 2026-11-21)
- **Consumer.** The `process-messages` Edge Function claims up to 5 jobs at a time from pgmq `process_message` (180-second visibility, so a crash is retried), parses each, uploads kept attachments to the private `attachments` bucket, and calls `record_parsed_message`. pg_cron calls it every minute through `private.call_edge_function`. Five failures mark the message `failed`. Like `storage-trash`, it only acts on queued jobs, so the public key is enough to call it.
- **Libraries,** pinned to releases more than two weeks old: postal-mime 4.2.0 (MIT-0; Cloudflare's Workers docs recommend it for MIME) and linkedom 0.18.14 (ISC; a DOM for HTML conversion). They're root devDependencies only so Deno can resolve `npm:` imports in this repo; the web app doesn't ship them.
- **Body choice.** Prefer `text/plain`, unless it's a "view in browser" stub or under 20% of the HTML's text; then convert the HTML.
- **HTML → text.** Data tables become `cell | cell` rows; layout tables (cells containing blocks) read as paragraphs. Links become `text (url)`, mailto links the address. Dropped: images, tracking pixels, scripts, styles, and hidden elements (`display:none`, `visibility:hidden`, `mso-hide:all`, `hidden`).
- **Forwards.** Gmail ("Forwarded message"), Apple Mail ("Begin forwarded message:") and Outlook (the `____` rule, or a bare From/Sent/Subject block) are unwrapped to the innermost original, up to 5 deep. Outlook writes the same block for replies, so it counts as a forward only under an `FW:`/`Fwd:` subject. "Forward as attachment" (a `message/rfc822` part) is parsed as the original. The original's sender, subject and sent date win; forwarders' notes are kept apart in `parse_details`.
- **Reference date** = the original's sent date. A forward header without a zone (Gmail's "Mon, Nov 17, 2026 at 9:14 AM") is read in the outer message's Date-header offset: an approximation, since the forwarder's zone usually matches. Fallbacks: the Date header, then the received time.
- **Quotes and signatures.** Cut at "On … wrote:", Outlook reply blocks, "Original Message", and `>` lines; signatures after `-- ` near the end; "Sent from my iPhone"-style lines. All of it goes to `stripped_text`. The spec said to keep it in Storage; a column with the same 30-day expiry does the same job with one less moving part.
- **Images.** Dropped when under 20 KB, under 300 px on the short side (read from PNG/GIF/JPEG/WebP headers), or named like logos, icons, social links or spacers. TNEF (`winmail.dat`), vCards and signature files are dropped too. Everything dropped is listed in `parse_details.discarded`, so an owner can see what was set aside. Identical files are stored once.
- **Language** is a small script-and-stopword guess (en, es, fr, de, pt, it, nl, and he, ar, ru, el, zh, ja, ko by script), or `und`.
- **Fixtures.** 26 invented emails, generated by `fixtures/build.ts`: newsletter, sports table, appointment, venue list, flyer image only, PDF only, Gmail/Outlook/Apple forwards, a two-level chain, a reply with a changed time, forward-as-attachment, quoted-printable, Latin-1 French, Spanish, Hebrew, an .ics invite, an inline poster, tracking/hidden content, a mobile signature, an Outlook reply that isn't a forward, duplicate attachments, winmail/vCard, base64 text, layout tables, and Outlook's numeric date. Expectations were written from each email's meaning before the first run. The first run caught a real bug (the "view in browser" pattern missed "View this email in your browser").
- **Limits of this phase.** The fixtures are built from documented formats and real-world shapes, not captured from real clients, so a real Gmail or Outlook forward may differ (the Phase 6 hand test will show it). Nothing reads `parsed` messages yet (Phases 8–9).

## D29 — Attachment triage, cheapest step first (Phase 8, 2026-11-21)
- **Flow.** `record_parsed_message` queues `triage_message`. `triage-attachments` (pg_cron every minute) reads each email's attachments in stages and records kept pages in `attachment_pages`, then queues `extract_message` for Phase 9.
- **Stage 0, the owner's rule** (`sources.attachment_rule`): `prefer` entries (filename pattern + type + pages) win outright, and the email's other files are skipped as `rule_other`. `never` entries skip. Patterns come from the picked file's name, lower-cased and regex-escaped with digit runs generalised, so `Schedule-Week-47.pdf` learns `^schedule-week-\d+\.pdf$`. The spec also mentioned a layout hash; it's left out because filename + page + type covered every test case and needs no page rendering. Revisit if real senders reuse one filename for different layouts.
- **Stage 1, metadata, no file reads.** Unsupported types (Word, Excel and the like for now), over 15 MB, receipt- or invoice-like names, and files already read in an earlier email to the same feed (same sha256) are skipped. "Read big files from this sender" lifts the 15 MB / 40-page limit.
- **Stage 2, text.** unpdf 2.1.0 (MIT) reads each PDF page's text layer. Pages are scored on months, weekdays, dates, times and event words, by density so long prose doesn't win on volume. Pages scoring 3 or more are kept, best first, **5 pages per email across all its files**: preferred pages, then .ics files, then score. `text/plain`, `text/csv` and `text/calendar` attachments are one page each.
- **Stage 4, vision last.** Photos, and PDFs with almost no text layer (under 40 characters a page), go to a vision model. Scans send only the owner's preferred page or their first 2 pages. Each PDF page is sent as a one-page PDF (pdf-lib 1.17.1, MIT) in a `document` block, so nothing has to be rendered. The model, `claude-opus-5-5` at effort `low`, is asked for a word-for-word transcription that treats instructions on the page as text; refusals fall back server-side (`fallbacks: "default"`) and are recorded as `vision_refused`. Anthropic's vision docs (checked 2026-11-21): images up to 8000×8000 px and 10 MB base64; current models downscale to a 2,576 px long edge, at most 4,784 tokens per image (⌈w/28⌉×⌈h/28⌉). That caps cost without our own resizing, which would need an image library in the Edge runtime; this replaces the spec's "1600 px". Images over 7 MB are skipped.
- **Vision is off unless `ANTHROPIC_API_KEY` is set** (in Supabase secrets). It costs money and the project is on free tiers, so photos and scans wait as `pending` with reason `needs_vision_not_configured` and the page says so. The SDK is `@anthropic-ai/sdk` 1.6.0, the newest release more than two weeks old. Tests use a fake transcriber, so **no real transcription has been run** (UNVERIFIED end to end).
- **Caps** per feed owner per day (`private.triage_limits()`): 300 text pages, 20 vision pages. Over the cap, files wait. Each attachment logs its stage, reason, kept pages and, for vision, tokens and an estimated cost at $4 / $20 per million input/output tokens.

## D30 — AI event extraction (Phase 9, 2026-11-21)
- **Where the code lives.** `supabase/functions/_shared/extract/` (Deno), not `packages/extract`. Only Edge Functions hold the API key, and parse and triage already live there; `packages/extract` now just points to it.
- **Flow.** Triage queues `extract_message`. `extract-events` (pg_cron, every minute) builds the input (clean text, kept pages, reference date, feed name, category and timezone), runs the pipeline, records `event_candidates` and queues `reconcile_message` for Phase 10. Message status: parsed → extracted, or needs_review.
- **Model calls.** `@anthropic-ai/sdk` 1.6.0 with structured outputs (`output_config.format` JSON schema, mirrored by a Zod schema). The build plan's routing: `claude-haiku-5-5` first (effort low); escalate to `claude-opus-5-5` (effort medium, server-side refusal fallback) when any event has confidence < 0.7, when the small model's output is invalid twice, or when the email is image-only. Each output is validated with Zod and retried once with the error. A refusal or a second invalid output means needs review.
- **Prompt-injection defence, in layers.** (1) The email and its pages are wrapped in tags, and look-alike tags inside the data are neutralised, so the email can't "close" its own block. (2) The system prompt says the data is untrusted, never to be followed. (3) A deterministic detector ("ignore … instructions", "system prompt", "as an AI", "add this event to the calendar") puts the whole message in needs_review and flags every candidate `possible_injection`, so nothing from it can publish automatically. A plain "please ignore the earlier flyer" doesn't trigger it (fixture 49).
- **Checks on every event** (`checks.ts`). A failure rejects the event, with the reason kept in `messages.extraction.rejected`:
  - the quote isn't in the named source, after normalising whitespace, curly quotes, dashes and case;
  - an unknown page;
  - a bad timezone;
  - a timed event whose quote has no time ("never guess a time");
  - an end before its start;
  - a date more than 31 days before or 550 days after the reference date;
  - a malformed RRULE.

  Softer signals send an event to review instead: confidence < 0.7 (lowered to 0.5 in D40), from a transcription, a change, or a cancellation.
- **Evaluation set.** 50 labelled fixtures with **recorded, hand-written model replies**. They include the mistakes the checks exist for: invented events, guessed times, paraphrased quotes, wrong pages, bad zones, an end before a start, past mentions, malformed JSON, and replies that obey planted instructions. In CI this measures **Feedcal's pipeline and checks, not the model.** Baseline: precision 0.939 over all candidates, **1.0 over events that could publish without review**, recall 0.902 (the misses are events correctly rejected for bad output), date and time accuracy 1.0, 0 unquoted events, 0 injected events that could publish. CI fails if a metric drops more than 3 points. Also hard-coded: unflagged precision ≥ 95%, date accuracy ≥ 95%, every event quoted, no injected event publishable.
- **Not verified:** the real models' precision, recall and injection resistance. That needs `EVAL_LIVE=1` with an API key (paid). The pass bar of "at least 95% precision on dates" is met only on recorded replies.
- **Without a key** (the free-tier default), messages wait at extraction ("waiting", `no_api_key`) and `requeue_waiting_extractions()` sends them back once a key exists (SETUP §8). Cap: 60 AI calls per owner per day; each call's tokens and estimated cost are logged (Haiku 5.5 $0.10/$0.50, Opus 5.5 $4/$20 per million tokens, from the cached claude-api reference).

## D31 — Matching updates to existing events (Phase 10, 2026-11-21)
- **In SQL, not an Edge Function.** Matching is set logic over the feed's events, so `reconcile_pending()` runs inside Postgres on pg_cron every minute, draining `reconcile_message`. It's tested directly with pgTAP and needs no API key.
- **Matching** (`private.match_candidate`): events in the same feed within ±14 days, or a weekly series with an occurrence at that time. Score = 0.6 × title trigram similarity (pg_trgm), + 0.2 for the same thread (subject with Re/Fwd stripped), + 0.1 for a similar location, + 0.1 for closeness in date. A title similarity of 0.35 or more is needed (0.2 within the same thread).
- **Outcomes:**
  - **duplicate**: same start and a similar title, so nothing new; it fills in a missing location.
  - **update**: the email says "changed" and a match exists. Start, end and location move, SEQUENCE goes up, and a `matched_update` revision records before and after plus the quote.
  - **cancel**: status becomes cancelled. The event stays in feeds for 30 days so calendars remove it, with a `cancelled` revision and the quote.
  - **exdate**: one occurrence of a series is cancelled; the date is added to `exdates`, the series stays, and SEQUENCE goes up.
  - **conflict**: same day, similar title, different time, but not stated as a change, so it goes to review.
  - **new**: anything else.
  - **unmatched_change**: a cancellation with no match goes to review.
- **Never deletes.** No code path deletes an event; the test counts events before and after a second run.
- **Auto-apply rule** (build plan): confidence ≥ the feed's threshold (default 0.85) **and** a trusted sender **and** no review reasons (low confidence, from a transcription, possible injection). Otherwise new events are created as unpublished drafts (`tentative`), and updates, cancellations and conflicts wait as `needs_review` candidates for the review screen (Phase 11), which also moves the message to needs_review.
- **Change to Phase 9:** "changed"/"cancelled" are no longer automatic review reasons. Before, a trusted school's "practice moves to 6 PM" could never reach subscribers without the owner acting, against this phase's "time change shows up in a subscribed phone calendar". Rain dates and other unsure changes still go to review through low confidence.
- **EXDATE** in the calendar output, in DTSTART's form (a DATE for all-day series, TZID local time otherwise). ical.js confirms the occurrence is skipped. Only weekly rules are matched for single occurrences (`private.occurs_at`), which covers practices; other rules are treated as separate events.
- **Not verified:** a time change seen updating in a real subscribed phone calendar (needs the hosted deploy and a phone). What's proven: SEQUENCE goes up, DTSTAMP and LAST-MODIFIED follow `updated_at`, and the .ics parses (D22, D24).

## D34 — Public directory (Phase 13, 2026-11-21)
- **Visibility is enforced by the database.** `directory_search` is SECURITY INVOKER and the web app calls it with the anon key and **no session**, so RLS (`feeds_anon_select_public`) and anon's column grants decide what it sees: public feeds, safe columns only. Directory, near, sitemap and robots pages don't touch the session, so they set no cookie and can be cached publicly (5 minutes).
- **Search**: full text on the feed's generated tsvector, plus pg_trgm `word_similarity` against name + city + category, so typos in a short query still match ("socer" 0.63, "libary" 0.50, "pizza" 0.17; threshold 0.45, measured). **Near**: PostGIS `ST_DWithin` on geography, 5, 10 or 25 miles (capped at 50); a feed's point follows its ZIP (trigger).
- **Ranking** = 3 × text rank + 2 × word similarity + 2 × closeness within the radius + 0.5 × ln(1 + followers) + freshness (+1 if updated within 30 days, −2 after 90) + 0.5 if verified. The follower number comes from `private.public_subscribers` (SECURITY DEFINER; returns 0 unless the feed is public). Stale feeds are labelled "may be out of date".

Tests use fake 999xx ZIPs.
- **Imported feeds.** Operator-added public calendars (`add_imported_feed`), fetched daily by `import-feeds` (HTTPS only, 15 s, 2 MB; ical.js 2.2.1). A TZID with no VTIMEZONE in the file, or a floating time, is read as wall-clock time in that zone (or the feed's zone), because ical.js would otherwise use the server's own zone. CI (UTC) caught this; the whole suite now also passes under TZ=UTC and TZ=Asia/Tokyo. Events are upserted by their source UID; events that disappear from the source are cancelled (kept 30 days), never deleted. Each is labelled with its source. **No real sources are listed:** which third-party calendars to republish is the owner's decision.
- **SEO:** server-rendered pages, `sitemap.xml` (public feeds only), `robots.txt` (keeps calendar files, accounts and management pages out), and schema.org `ItemList` of `Event` JSON-LD on public feed pages, with `<` escaped so event text can't end the script.

## D37 — Security hardening and privacy (Phase 16, 2026-11-21)
- **Threat model and review.** `docs/THREAT-MODEL.md` has STRIDE risks T1–T15, each with an owner, a fix and a status. `docs/SECURITY-REVIEW.md` checks the OWASP Top 10:2025 (list checked at owasp.org on 2026-11-21): **8 pass, 2 partial** at first (A03: older actions pinned by tag; A09: no alerting until Phase 18). A03 was fixed the same day (see the follow-up below), so it was **9 pass, 1 partial**, and A09 passed with Phase 18 (D38): **10 of 10**. `docs/AGENT-ACCESS.md` covers what an AI coding agent may hold.
- **Headers.** One function sets them on every response, keeping a route's stricter value. Feeds and subscribe hand-offs send `no-referrer`. Before this, the middleware overwrote that with `same-origin` on every response, a bug this phase fixed. The headers:
  - CSP: `default-src 'none'; script-src 'self'; style-src 'self'; style-src-attr 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; form-action 'self' <supabase> https://accounts.google.com; frame-ancestors 'none'; base-uri 'none'`.
  - Also HSTS, nosniff, COOP, a Permissions-Policy, and `X-Frame-Options`.

  Inline scripts are gone. The copy button, the undo countdown and the print button now use data attributes and one script, `/assets/app.<hash>.js`; the stylesheet moved to `/assets/app.<hash>.css`. Both are cached for a year. Inline style attributes stay allowed through `style-src-attr` because they can't run code (browsers without CSP3 `-attr` support fall back to `style-src` and just lose that styling). The JSON-LD block is a data block, not a script. `form-action` includes Supabase and Google because "Continue with Google" is a form post that redirects there. Subscribe buttons are links, not forms, so the calendar hosts aren't needed. HSTS starts at one day (`HSTS_MAX_AGE` raises it; SETUP §13).
- **Keys into Vault.** The unsubscribe HMAC key and the sign-in salt were plain tables, so a dump would have let someone forge unsubscribe links or test guesses against the salted hashes. They're now Vault secrets, with their values carried over, so links already sent still work. Views with the old names mean no function changed. Feed tokens were already hashed plus Vault (Phase 2). pgTAP 018 checks that Vault's stored column holds neither the token nor the key. **Kept as is:** `fetch_salts`, the daily salt for counting calendar fetches. It's deleted after 2 days, so a dump links fetch counts to devices for at most that window.
- **Rate limits.** One limiter (`private.rate_ok`) stores salted hashes, never addresses.
  - `/f/` misses: 30 per 10 minutes per address, then 429 with Retry-After 600, even for a real token. Google's and Microsoft's fetchers are exempt: they fetch for many people from shared addresses, and old links after a rotation would otherwise lock a whole provider out.
  - Directory search: 60 a minute.
  - Subscribe taps: 30 a minute, past which they aren't counted; the hand-off still works.
  - Already limited: sign-in emails and both report forms. Webhooks: signature first.

  **Limit of the design:** the address comes from the web app (`cf-connecting-ip`). A direct API caller with the public anon key picks its own, so the API path relies on 256-bit tokens and Supabase's platform limits (UNVERIFIED). Revoking anon's `feed_calendar` grant would protect nothing for that reason, so it stays.
- **PDF safety.** Refused before parsing: files that aren't PDFs despite their type, and encrypted files (`pdfRefusal`). Each parse has a 20-second limit (`too_slow`), and the parser's memory is freed after each file. Embedded JavaScript is never run: text extraction doesn't execute scripts, the bundled pdf.js has no `eval` or `new Function` (grep of `unpdf` 2.1.0's bundle), and vision pages are copied into a fresh PDF. Isolation: parsing runs in its own Edge Function, not in the web app. Its memory limit is Supabase's (value UNVERIFIED).
- **Privacy.**
  - `/account/export` downloads everything about you as JSON: account, profile, settings, supporter status, and feeds with events, senders and email records. Token hashes and Vault ids are left out. `/account/export/<feed>.ics` gives each feed's events.
  - `/privacy` is a plain-English draft. Its retention list matches DATA-MODEL's "Where personal data lives" and asks people not to forward medical or other sensitive details.
  - Cookies are session-only (the Supabase session and the CSRF cookie).
  - New retention job: fetch counts kept 400 days; sent email contents emptied after 30 days.
  - **Gap closed:** account purges were never scheduled (SETUP said so). pg_cron now calls `delete-accounts` daily with the anon key, like `storage-trash`. It only purges accounts already past their 14 days, so a stranger calling it can't delete anything early. The service-role check inside it was removed for that reason.
  - A deleted account's linked supporter record is now deleted, not just unlinked.

## D39 — Gmail connection: one sender, on a schedule (Phase 17, 2026-11-21)
- **The design comes from the owner** (2026-11-21), replacing the build plan's "one label, push via Pub/Sub":
  1. Connect Gmail (read-only).
  2. Search for one **example email**: the owner's own words, over the last 30 days, showing at most 10 results with sender, subject and date only.
  3. Feedcal shows **what it will do**: only emails from that sender, how often, and the example read first. Nothing is saved until **Confirm**.
  4. It checks every **3 or 7 days** (the owner's choice), asking Gmail only for `from:<sender> after:<last check>`.

  Nothing else in the mailbox is searched or read. The sender always comes from a real email in the owner's own search results; free-typed senders aren't accepted. A sender is also checked against a strict address pattern before going into a query, so no extra search terms can ride along (tested).
- **Why not 14 days:** in "Testing" mode, Google gives an app asking for more than basic scopes "a refresh token expiring in 7 days", and caps it at 100 test users (developers.google.com/identity/protocols/oauth2 and …/production-readiness/overview, read 2026-11-21). A 14-day schedule would expire before its second check. Feedcal emails the owner a reminder a day before expiry, and again if Google refuses the token. Reconnecting keeps the sender and schedule. Lifting both limits needs Google's restricted-scope verification, which includes a paid security assessment; the details are UNVERIFIED and it's the owner's decision. 14 days can be added then.
- **Why not Pub/Sub:** it needs a Google Cloud billing account. Checks that are days apart don't need push. pg_cron calls `gmail-poll` every 5 minutes, but only connections whose next check is due are touched, so a newly confirmed example is read within minutes.
- **One intake.** Gmail's raw copy of each email (`format=raw`) goes through `ingest_start` and `ingest_commit`, exactly like a forwarded email. That means the same dedupe, new-sender approval, DMARC quarantine, daily cap, 30-day retention and AI pipeline. `private.gmail_messages` records which Gmail message became which Feedcal message, for dedupe and deletion.
- **Tokens.** The refresh token lives in Vault. The web app never sees a Google token: Edge Functions hold them, and the owner's example search runs in `gmail-search`, which first checks ownership with the owner's own session. The OAuth flow uses a one-time state (only its hash is stored, valid 10 minutes) and PKCE (S256). `prompt=consent` and `access_type=offline` ensure a refresh token. "Disconnect Gmail" deletes the token, asks Google to revoke it (pg_net), and deletes every message copy that came from Gmail, at once. Deleting the feed or account removes the token too (trigger).
- **Logs** hold counts and outcomes only, never the search words, senders or subjects.
- **Tests:** pgTAP 020 covers owner-only access, state reuse, Vault, examples limited to the owner's results, 3/7 days only, schedule moves, failed checks, reconnects, reminders and disconnect. Deno tests use a fake Google to prove one search per check, only for the sender, and metadata only while searching. Web tests cover the PKCE redirect, the 3/7 choice, the confirmation saving nothing until Confirm, and non-owners refused.
- **Not verified:** a real Google account end to end. It needs the owner's Gmail Google Cloud project, client id and secret (SETUP §15). The build plan's "labelling updates the feed within 2 minutes" no longer applies to this design; what applies is "a confirmed example is read within about 5 minutes, then checks every 3 or 7 days" (unverified live).

## D41 — Date rules decide auto-publishing, for every feed (2026-11-21)

- **Why.** The owner: auto-publishing should be universal, and "the logic gates need to be enough to not make errors". The model's self-rated confidence alone isn't a good enough gate: the Room F "This Friday" email (sent on a Friday) scored 0.55 for a genuinely ambiguous date, and a high score can still be wrong.
- **The rules** (`supabase/functions/_shared/extract/dates.ts`, no model involved). Each event's date and time are checked against its `evidence_quote` and the email's sent date, taken in the event's time zone:
  - A **written date** ("Nov 20", "November 20th, 2026", "20 November", "11/20", "2026-11-20") must include the event's date, or it's `date_mismatch`. A weekday written with it must agree (`weekday_mismatch`).
  - With no written date, a **relative day** ("today", "tonight", "tomorrow", "this/on/coming Friday", "next Friday") is counted from the sent date. Exactly one possible date that matches: proven. More than one ("this Friday" sent on a Friday; "next Friday" sent mid-week): `ambiguous_date`. None matching: `date_mismatch`. "Last/past Friday" is ignored.
  - An event **before the sent date**: `before_email`.
  - A timed event: any **written time** ("3pm", "4:30 p.m.", "15:30", "noon") must include the start time, or it's `time_mismatch`.
- **The decision** (`private.reconcile_candidate`). Publish when the sender is trusted, there are no review reasons, and either confidence ≥ the feed's bar (0.85 unless changed) or the date is proven (`event_candidates.date_confirmed`) and confidence ≥ 0.5. Every new reason above is a review reason, so it always waits for the owner, with a plain explanation on the review screen. Unapproved senders always wait. Escalation to the large model (< 0.7) is unchanged.
- **Room F.** Under these rules the Nov 20 "Dinos-giving" event is `ambiguous_date` and would still wait, which is the intended outcome for an email that could mean either Friday.
- **Not covered.** Day-first dates (20/11) are read as month/day, so a UK-style 20/11 doesn't match and goes to review (safe, not silent). Words like "next week" or "after Thanksgiving" prove nothing, so those fall back to the feed's bar. The rules don't re-run on events already decided. Accuracy on real mail beyond the Room F emails isn't measured yet.

## D59 — Close a location loophole; harden the prompt guard; stricter sign-in redirects (2026-11-21)

- **How it was found.** CodeQL's first scan (D58 follow-up) flagged two lines. Both were false alarms on the lines themselves, but tracing what each warning was about found three real issues.
- **Location loophole (fixed, `20261121002300_duplicate_location_gate.sql`).** When an email repeated an event already on the calendar, `reconcile_candidate` filled in a missing location before any trust check, so a stranger's email could add a location families would see. Now only a trusted sender with no review reasons can. `supabase/tests/025` failed before the fix (the stranger's location was written) and passes after.
- **Prompt guard (`prompt.ts`).** CodeQL's "only the first `<` is replaced" was wrong: each match holds one `<`. But invisible characters (`<\u200b/body>`), full-width `＜`, `&lt;`, look-alike letters (Cyrillic `о`) and other slashes got through. Untrusted text now loses Unicode format characters (Cf) and is NFKC-folded before the model sees it, and fake tags are matched across bracket look-alikes, entities, escaped forms, slash variants and look-alike letters. `checks.normalise()` applies the same cleaning (and reads `‹` as `<`), so evidence quotes still match the original email. `prompt.test.ts` generates 125,891 attack strings and checks them with a separately written "how a model might read it" detector: the old guard left 125,589 looking like our tags; the new one leaves none. Ordinary text (other languages, `<3`, `a < b`, links in `<>`) passes unchanged.
- **Sign-in redirect (`security.ts` `safeNext`).** It already kept people on the site; 20,592 generated tricks (schemes, slash and backslash forms, encoded and invisible characters, user@host, look-alike dots) confirm it. They also showed a `next` with characters above U+007E passed the check but couldn't be sent as a Location header, so sign-in ended on an error page. Only printable ASCII is accepted now; our own paths are all ASCII.
- **Email test (`notify.test.ts`).** Checks the reconnect link as an exact link, not "somewhere in the text".
- **Limits.** The guard is one layer: the trusted-sender gate, evidence quotes and injection phrases still decide what publishes. The detector's idea of "looks like our tag" is a generous assumption, not a measured model behaviour.

## D70 — The standard bar is 70%; unclear days are reasoned out; no stated time means all-day (2026-11-23)

  - *Bar.* The default in `private.reconcile_candidate` (and any other function carrying it) goes from 0.85 to 0.70, by migration `20261124000100_publish_bar_70.sql`, which rewrites the current definitions in place. ## D76 — Reading the same email again never adds a second copy (2026-11-23)

- **Why.** On production, Room F's three emails were re-read twice in one day (D71, D74). Afterwards its review page held five cards, among them "No school (Thanksgiving)" on Nov 26 and "No school - Thanksgiving" on Nov 27 from the same newsletter line, and a "change" card for a Share Day already on the calendar. The owner: "I want to fix the dupe issue where an email is re read, to avoid multiple of the same event every time its read".
- **Cause.** `reconcile_candidate` treated every read as a new email. `match_candidate` needs the same start time to call something a duplicate, and the model's wording and even its chosen day vary between reads, so a re-read fell through to "new". `record_extraction` cleared only `pending` candidates, so undecided review cards from the earlier read stayed.
- **The rule.** A re-read can only refine what that same email (`events.source_message_id`) produced before.
  - `record_extraction` also drops the email's `needs_review` candidates before recording the new read.
  - In `reconcile_candidate`, before the normal matching: if the candidate looks like an event this email already produced, it is that event. An undecided draft (unpublished, tentative) takes the newer reading and is published if it now qualifies. A published event, or a draft the owner discarded, is left as it is. Either way the candidate is recorded as `duplicate` and no card appears.
  - If it looks like a candidate the owner rejected from this email, it is recorded as `duplicate` and nothing appears.
  - "Looks like": title trigram similarity of 0.5 or more, or the same start with similarity of 0.2 or more.

## D77 — Safeguards for publishing without the owner (2026-11-23)

## D83 — Time rules: a range shares its AM/PM, and an end time must be stated (2026-11-24)

- **Why.** The owner asked whether a time in an email is sure to reach the calendar correctly. Fourteen phrasings were run through `dateGate` (a scratch script, not kept in the repo). Three gaps showed in that run:
  1. "6:30-8 PM" was read as 6:30 with no AM/PM plus 8 PM, so a correct 6:30 PM start was held as a mismatch.
  2. "at 3:15" matched both 3:15 AM and 3:15 PM, so either reading counted as proven.
  3. Nothing checked an end time against the words. A model's guessed length was stored.
- **What.**
  - `timesIn` (`extract/dates.ts`) reads ranges first. An AM/PM on the end of a range applies to the start; if that would put the start after the end, the start is the other half ("11-1 PM" is 11 AM to 1 PM).
  - `timeStated` answers `yes`, `maybe`, `unlikely`, `no` or `silent` for a clock time against a text. Only `yes` proves a time (`dateGate`, and `timeProven` in `extract/pipeline.ts`).
  - `withoutUnstatedEnd` now also drops an end time the quote does not state (`no` or `silent`). The event is kept with no end.
- **Changed behaviour in the 50-fixture evaluation.** Fixture `40-end-before-start` (start 7 PM, end 5 PM, quote "7 PM") used to be rejected whole. Its end is now dropped and the event kept. The `end_before_start` check stays in `checks.ts` for ends the words do state.
- **Tests.** `extract/dates.test.ts`, `extract/resolve.test.ts`, `extract/eval/eval.test.ts`.
- **Not covered.** An hour with no colon and no AM/PM ("at 9", "9 o'clock", "1830") is not read as a time. Such an event has no time in its words and becomes all-day (D70).

## D84 — With no AM/PM, 7 to 11 is morning and 12 to 6 is afternoon; no end time means a one-hour block (2026-11-24)

- **Owner's rules, given while D83 was being built.** "The times are likly AM 7-11, and pm 12-6, so that should be factored in, almost like a rule if not specificied", and "if no end time, only give it an hour block."
- **What, for AM/PM.**
  - `timesIn` gives a time with no AM/PM its likely reading by those hours, and keeps the other reading as `other`. In a range with no AM/PM ("6:30-8", "11:30-1"), the start follows the rule and the end is the first such time after it. A range needs at least one side written H:MM, so "Nov 20-21" is not a time.

  - The prompt tells the model the same rule.
- **What, for the hour block.** `packages/ics/src/calendar.ts` writes `DTEND` one hour after `DTSTART` for a timed event with no stored end. The stored event still has no end, and Calantern's own pages still show the start time only. All-day events are unchanged.
- **Effect on existing events.** Every timed event with no end, on every calendar, is served with the one-hour end from the next time its feed is built. Read from the code; no calendar app was checked for how it redraws an event whose end appears without a new `SEQUENCE`.
- **Tests.** `extract/dates.test.ts` (the hours, ranges, the settling words, the review reason), `packages/ics/src/calendar.test.ts` and the golden files.
- **Not covered.** Events at unusual hours for the rule (a 7:00 evening concert with no "evening" in the quoted words) will wait for the owner. That is the intended cost.

  - `chat_report(message, ip)`: three reports from different addresses hide a message. The organizer's own messages can't be reported away. `chat_remove(message)`: members only.
  - **Open** means switched on, the event published and not cancelled, the calendar not hidden, and the event not over. An event with no end time counts as an hour long (D84); an all-day event lasts through its last day; a repeating event stays open while it has a coming date.
  - Pages: `GET/POST /chat/<event uid>`, `/chat/<uid>/messages` (the list alone), `/report/<id>`, `/remove/<id>`. The page script fetches the list every 5 seconds while the page is in view. No third-party service and no browser-side database key are involved.
  - The event edit page has the switch. An event with an open chat gets "Chat about this event: <link>" in its description.
- **Limits of the moderation, stated plainly.**
  - Nothing reads a message before it is shown. A harmful message is visible until the organizer removes it or three people report it.
  - The no-links rule is a pattern, not a guarantee: "example dot com" passes.
  - Two followers behind one network address (a school's Wi-Fi, a home) share one made-up name and one posting limit. One person on two networks gets two names, and so can report twice.
  - With the web server's proof of address missing (local runs), every follower shares one name.
  - The organizer is not told when a message is posted or reported; they have to look.
  - No lawyer has reviewed hosting followers' messages. `/rules` and `/terms` were not changed.
